# Resume Pack 终局 PRD

> 状态：产品终局需求稿  
> 适用范围：TypeDance Resume Pack 的产品定义、交互目标、后端能力、Agent 能力、验收标准  
> 重要说明：本文不是渐进式实施计划，而是目标产品形态。后续任何阶段性开发都必须朝这个形态收敛。

## 1. 产品定义

Resume Pack 是 TypeDance 的第一个 Document Pack。

它不是简历模板工具，也不是富文本编辑器加 AI 聊天框，而是一个面向求职者的 AI-native 简历改稿系统。

它的核心任务是：

```text
把旧简历、空白信息、零散材料和用户补充
转化为一份可信、清晰、可投递、可持续调整的结构化简历。
```

Resume Pack 必须让用户感觉：

```text
我不是在从零写简历。
我是在和一个懂简历、懂表达、懂风险的系统一起完成一份正式稿。
```

## 2. 产品立场

### 2.1 简历优先是“基础简历”，不是 JD 优先

大多数用户不是为了某一份 JD 才开始写简历。

更常见的过程是：

```text
先做一份能代表自己的基础简历
-> 去招聘软件浏览机会
-> 对看起来合适的岗位做局部调整
-> 投递或和 HR 沟通
```

因此 Resume Pack 的默认主线必须是：

```text
基础简历生成 / 旧简历重构 / 简历质量改稿
```

JD 是后续的机会校准场景，不是唯一入口。

### 2.2 AI 不应该表现成一个孤立聊天框

用户面对“你想让我怎么帮你”的聊天框时，往往不知道怎么提问。

Resume Pack 的 AI 应该融入操作路径：

- 用户点击“导入旧简历”，系统自动进入解析、重构、诊断、生成新稿。
- 用户点击“补充工作经历”，系统用表单、追问、示例和建议引导，而不是要求用户写 prompt。
- 用户点击问题卡，系统展示旧表达、新表达、修改理由、证据状态和可执行动作。
- 输入框存在，但它是补充事实、表达偏好和临时沟通入口，不是主交互。

### 2.3 模板和主题不是核心竞争力

Resume Pack 必须有一个高质量默认模板。

这个默认模板应当：

- 专业。
- 克制。
- A4 友好。
- ATS 友好。
- 适合大多数知识工作者。
- 稳定支持中文和英文排版。

但模板市场、主题库、花哨样式、复杂样式面板不是现阶段核心。

在 AI-native 改稿能力未完成前，主题概念不应作为产品重点维护。

## 3. 目标用户

### 3.1 主用户

- 有旧简历，但质量不满意的人。
- 想写简历，但看到工作经历、项目经历、技能、自我评价就卡住的人。
- 有实际经历，但不知道如何提炼成果和表达价值的人。
- 需要一份基础简历，再根据机会做小幅调整的人。

### 3.2 次用户

- 应届生、实习生、转行用户。
- 工作多年但经历杂乱的人。
- 需要中英文简历的人。
- 对高价值岗位需要额外定制的人。

### 3.3 非核心用户

- 只想下载大量花哨模板的人。
- 只想让 AI 编造经历的人。
- 只需要普通在线文档编辑器的人。

## 4. 核心成功标准

Resume Pack 成功时，用户应完成以下结果：

1. 不从空白开始，也能得到第一份可编辑的简历草稿。
2. 导入旧简历后，系统能指出具体问题，而不是泛泛说“建议优化”。
3. 用户不需要写 prompt，也知道下一步该做什么。
4. 系统能把“弱表达”变成“更具体、可信、结果导向的表达”。
5. 系统能区分事实、推断、建议和风险，不把虚假内容静默写入简历。
6. 用户可以接受、拒绝、回退和追踪每一次重要修改。
7. 最终导出的 PDF 是可投递的，不需要用户再去别的软件重新排版。

## 5. 核心工作流

### 5.1 导入旧简历

入口：

```text
导入旧简历
```

用户可以上传 PDF、DOCX、Markdown、HTML、图片 OCR 结果，或直接粘贴旧简历文本。

系统动作：

1. 解析旧简历。
2. 识别简历模块。
3. 抽取个人信息、经历、项目、技能、教育等结构化数据。
4. 识别重复、空泛、弱证据、时间线异常、表达不清、模块缺失等问题。
5. 用默认模板生成新版草稿。
6. 生成问题卡和修改说明。

用户看到的不是一段聊天回复，而是：

```text
新版简历草稿
+ 待处理问题
+ 局部对比
+ 修改原因
+ 可执行动作
```

### 5.2 从空白开始

入口：

```text
新建简历
```

系统不能把用户扔进空白编辑器。

系统应根据 Resume Pack 的模块结构引导用户：

- 先填写基本信息。
- 再选择身份状态，例如社招、应届、实习、转行、管理者。
- 再按用户身份决定优先补充哪些模块。
- 对难写模块使用问题式引导。

例如工作经历不能只给一个大文本框，而应拆成：

```text
你在哪家公司做过什么角色？
负责什么业务或系统？
最重要的 2-3 件事情是什么？
有没有数字、范围、结果或影响？
这段经历想突出什么能力？
```

系统根据回答生成结构化初稿，并标记待确认内容。

### 5.3 补充材料

用户可以添加：

- 工作总结。
- 项目文档。
- 周报、述职、复盘。
- 作品链接。
- Git 仓库说明。
- 过往简历。
- 用户手动输入的事实片段。

系统应将这些材料转化为：

```text
SourceDocument
ParsedBlock
EvidenceLink
CandidateClaim
```

补充材料不应直接污染简历正文。它们先进入证据和候选主张池，再由系统提议是否写入简历。

### 5.4 基础简历质量改稿

系统必须支持不依赖 JD 的质量优化。

质量改稿包括：

- 模块完整性检查。
- 时间线检查。
- 个人信息风险检查。
- 经历表达质量检查。
- 技能和经历一致性检查。
- 成果表达具体性检查。
- 自我评价套话检查。
- 篇幅和重点检查。
- 可信度和证据检查。

输出必须是问题卡，而不是聊天建议。

### 5.5 机会校准

当用户有目标岗位或招聘信息时，可以进入机会校准。

入口可以是：

```text
针对岗位调整
```

用户提供 JD、岗位截图 OCR、招聘链接文本、公司信息或手动描述。

系统动作：

1. 提取岗位能力要求。
2. 评估当前基础简历匹配度。
3. 找出可强化模块。
4. 从已有经历中选择更相关表达。
5. 生成岗位版本。
6. 标记风险：缺少证据、过度匹配、关键词堆砌、与真实经历不一致。

机会校准是 Resume Pack 的重要能力，但不能反过来绑架基础简历主线。

## 6. 核心页面形态

### 6.1 默认工作台

默认工作台以新版草稿为主角：

```text
顶部：
文档名 / 当前版本 / 质量状态 / 导出 / 版本 / 模式

主体：
新版简历草稿

侧边：
问题卡、待确认事项、补充入口、导出检查
```

旧简历、来源材料和完整对比默认不常驻占用主空间。

### 6.2 局部对比

用户点击问题卡后，进入局部对比视图：

```text
旧表达
新版建议
修改原因
证据来源
风险提示
可执行动作
```

可执行动作包括：

- 接受修改。
- 保留原文。
- 让表达更保守。
- 让表达更具体。
- 补充事实。
- 查看来源。
- 改成另一种语气。

### 6.3 小屏布局

小屏不强行左中右三栏。

应采用：

```text
主稿件
+ 底部/右侧问题抽屉
+ 来源抽屉
+ 局部对比弹层
```

原则是：

```text
任何屏幕尺寸下，用户都要知道当前正在处理哪一个问题，以及处理后会影响哪一段简历。
```

## 7. 功能需求

### 7.1 来源导入

必须支持：

- 粘贴文本。
- 上传旧简历。
- 导入常见文档格式。
- 添加手动材料。
- 保存来源和解析结果。
- 标记来源类型。

系统必须保留原始来源，不允许只保存 AI 整理后的文本。

### 7.2 简历解析

必须识别：

- 基本信息。
- 求职意向。
- 职业摘要。
- 核心技能。
- 工作经历。
- 项目经历。
- 教育经历。
- 实习经历。
- 证书奖项。
- 作品链接。
- 自定义模块。

解析结果必须允许用户修正。

### 7.3 结构化草稿

新版简历必须保存为结构化 Draft，而不是只保存富文本。

Draft 至少包含：

- 模块列表。
- 模块顺序。
- 模块可见性。
- Claim 列表。
- EvidenceLink。
- Issue。
- Proposal。
- RenderProjection。

### 7.4 问题诊断

系统必须生成具体问题卡。

问题卡应包含：

- 问题标题。
- 问题类型。
- 影响模块。
- 严重程度。
- 当前表达。
- 建议方向。
- 可执行动作。
- 是否阻塞导出。

问题类型至少包括：

- 信息缺失。
- 表达空泛。
- 缺少结果。
- 缺少证据。
- 时间线异常。
- 技能和经历不一致。
- 内容重复。
- 篇幅过长。
- 语言风格不统一。
- 可能不适合 HR 阅读。
- 可能存在夸大风险。

### 7.5 修改建议

AI 修改建议必须保存为 `RevisionProposal`。

每条 Proposal 必须能回答：

```text
改哪里？
原来是什么？
建议改成什么？
为什么改？
依据是什么？
风险是什么？
用户可以做什么？
```

不允许只有自然语言说明，没有结构化修改对象。

### 7.6 用户确认

以下内容必须需要用户确认：

- 新增的具体数字。
- 强成果主张。
- 职级、职责范围、团队规模。
- 任何来源中没有直接支撑的经历细节。
- 可能改变事实含义的改写。

用户确认后，应记录确认状态和时间。

### 7.7 版本管理

系统必须区分：

- 导入版本。
- AI 初稿版本。
- 用户编辑版本。
- 岗位定制版本。
- 已接受版本。
- 已导出版本。

用户应能回到旧版本，查看重要修改历史。

### 7.8 默认模板与导出

Resume Pack 必须提供一个默认可投递模板。

导出前必须经过质量检查：

- 是否有阻塞问题。
- 是否有未确认强主张。
- 是否有明显排版溢出。
- 是否缺少联系方式。
- 是否存在敏感或不建议公开的信息。

导出格式至少包括 PDF，后续可以支持 DOCX、Markdown、HTML。

## 8. Agent 能力要求

Resume Pack 至少需要以下 Agent 能力。

### 8.1 Parser Agent

负责解析旧简历和材料。

输出：

- ParsedBlock。
- 初始模块识别。
- 候选字段。
- 解析置信度。

### 8.2 Resume Structurer

负责将解析结果转为 Resume Pack 模块。

输出：

- DocumentModule。
- DocumentClaim。
- 字段缺失。
- 模块顺序建议。

### 8.3 Resume Reviewer

负责发现简历问题。

输出：

- RevisionIssue。
- 严重程度。
- 阻塞状态。
- 影响范围。

### 8.4 Resume Rewriter

负责生成修改建议。

输出：

- RevisionProposal。
- before / after。
- 修改理由。
- 证据关联。
- 风险提示。

### 8.5 Evidence Verifier

负责检查主张是否有来源支撑。

输出：

- EvidenceLink。
- confidence。
- support_type。
- 是否需要用户确认。

### 8.6 Opportunity Calibrator

负责根据目标岗位调整简历版本。

输出：

- 岗位能力结构。
- 匹配度分析。
- 模块强化建议。
- 岗位版本草稿。
- 过度匹配风险。

### 8.7 Render Planner

负责把结构化 Draft 投影到默认模板。

输出：

- RenderProjection。
- 模块渲染顺序。
- 分页风险。
- 篇幅压缩建议。

## 9. 后端支撑要求

Resume Pack 依赖 Revision Engine。

后端必须提供：

- Source Service：保存来源和解析块。
- Draft Service：保存结构化草稿。
- Issue Service：保存问题卡和处理状态。
- Proposal Service：保存修改建议和用户决策。
- Evidence Service：保存证据关系和确认状态。
- Render Service：生成 HTML、doc_json、PDF 输入。
- Revision Orchestrator：编排一次完整改稿任务。
- Pack Registry：加载 Resume Pack 的模块、规则、动作和 schema。

前端不应直接消费 Agent 原始输出，而应消费 Workspace View。

## 10. 关键数据对象

```text
Document
SourceDocument
ParsedBlock
DocumentModule
DocumentClaim
EvidenceLink
RevisionRun
RevisionIssue
RevisionProposal
RevisionAction
DraftVersion
RenderProjection
ExportArtifact
```

这些对象是 Resume Pack 的产品事实源。

`doc_json` 只是渲染投影，不是简历事实源。

## 11. 模块管理如何体现

WPS 的模块管理在 Resume Pack 中不应被照搬为“手动增删区块”。

TypeDance 的模块管理应体现为：

```text
模块状态
+ 模块质量
+ 模块证据
+ 模块问题
+ 模块动作
+ 模块是否进入当前版本
```

例如：

- 工作经历模块显示“2 个表达空泛，1 个成果缺少证据”。
- 项目经历模块显示“可从项目材料中补充 3 条候选成果”。
- 自我评价模块显示“建议转为职业摘要或隐藏”。
- 技能模块显示“5 个技能没有在经历中体现”。

用户看到的是模块，但系统操作的是结构化语义对象。

## 12. 聊天入口定位

Resume Pack 可以有“和 AI 说一下”的入口，但它不是主界面中心。

聊天入口适合处理：

- 用户补充事实。
- 用户表达偏好。
- 用户解释背景。
- 用户临时提出具体修改。
- 用户对某个建议追问。

聊天输出不能直接写入最终简历。

聊天输出仍必须被转为：

```text
Issue
Proposal
Claim
Evidence
Draft patch
```

## 13. 低优先级和非目标

以下不是 Resume Pack 的核心优先级：

- 大量模板库。
- 主题市场。
- 花哨封面。
- 动效助手形象。
- 聊天机器人主界面。
- 让用户管理 prompt。
- 让用户手动调很多排版参数。

以下原则必须坚持：

- 不为了显得 AI 很强而牺牲可信度。
- 不为了视觉丰富而牺牲可投递性。
- 不为了聊天自由度而牺牲结构化改稿能力。

## 14. 验收标准

### 14.1 导入旧简历验收

给定一份旧简历，系统应能：

1. 解析出主要模块。
2. 生成新版结构化草稿。
3. 发现至少一组具体问题。
4. 展示旧表达和新建议。
5. 让用户接受或拒绝修改。
6. 导出默认模板 PDF。

### 14.2 空白创建验收

给定一个没有简历的用户，系统应能：

1. 引导填写基础信息。
2. 引导补充至少一段经历。
3. 根据用户回答生成初稿。
4. 标记缺失和待确认内容。
5. 不把用户留在空白编辑器里。

### 14.3 基础质量改稿验收

给定一份没有 JD 的基础简历，系统应能：

1. 生成质量诊断。
2. 标记弱表达和缺证据主张。
3. 给出可接受的修改建议。
4. 保留版本历史。
5. 在导出前提示阻塞风险。

### 14.4 机会校准验收

给定一份基础简历和一份目标岗位信息，系统应能：

1. 提取岗位要求。
2. 判断当前简历匹配点和缺口。
3. 生成岗位版本。
4. 标记过度匹配和缺证据风险。
5. 不虚构用户没有提供或确认的经历。

## 15. 与现有系统的关系

现有编辑器、A4 预览、PDF 导出是可保留资产。

但产品核心必须从：

```text
用户编辑 doc_json
+ AI 辅助润色
```

转为：

```text
Revision Engine 管理 Draft / Issue / Proposal / Evidence
+ Renderer 生成 doc_json / HTML / PDF
```

也就是说，编辑器仍然重要，但它不再是产品大脑。

## 16. 终局判断标准

如果一个功能让用户更像是在“自己写简历”，它不是核心。

如果一个功能让用户更自然地完成：

```text
理解自己
补充事实
看见问题
确认修改
得到正式稿
```

它就是 Resume Pack 的核心。
