# 0.1.11 上下文预算与缓存效率验证

日期：2026-10-27，Asia/Shanghai。基线提交 `11484d68203a7c3231bf5f9f4b323d30a3146f2b`，优化版本 0.1.11。真实模型为 `deepseek-flash`，凭据只通过临时环境注入，没有进入代码、报告或安装包。

## 改动

- Core 用同一已测请求的实际输入加新增片段预测输入量，替换无法下调粗估的旧公式。校准绑定模型/配置/system/tools/历史前缀；checkpoint 与跨轮恢复携带基线，历史替换后失效。
- Host 按真实模型容量 1,048,576 管理本轮策略；当前产品输入预算 160,000、软阈值 0.8，另预留输出和工具增量。并行运行的预算互不影响。服务地址变化时在 fetch 前拒绝继续，避免新凭据被发送给旧地址。
- 编辑能力改成目录加按需 schema，inspect 可按 outline/detail/layout 与节点路径查询；edit 和结束审查返回紧凑证据，保留实际决定、最新版本、保存状态与决策来源。
- live workspace 只投影发送时的资料引用，要求重新读取当前正文；压缩后不再将旧全文重新标成最新内容。

没有引入 Messages 协议迁移、无用长前缀或新的大结果文件存储。此轮先通过定向查询减少大结果；需要全文时仍可分页读取，没有直接把所有工具结果截成 1k。

## 三次完整八轮真实模型对照

使用同一脚本、合成简历、任务、模型、Off 模式和权限。每组 8 轮包含两次精确局部修改、后续资料核对和最后重建 Host/Runtime/数据库读取历史。每次都使用独立随机前缀。

下表使用完整基线 4–6 与最终实现 7–9，每个实现 3 次。早期另有交错运行的预验证；最终组分段串行，未隔离本机所有其他负载，因此耗时只作样本记录，不作为稳定加速承诺。

界面仍展示真实会话累计统计，历史调用不会因升级被重新计算。升级后的新工具定义与指令也需要重新预热；旧会话显示值会随后续调用逐渐变化。

工具事件原始 output 字符数中位数：capabilities 17,245 → 923，edit 7,850.5 → 347。它们是原始 JSON 字符数，不等于最终 provider token 数。inspect/read 的返回范围由模型按任务选择，不能只比较工具名称的字符数就推断整项任务收益。

成本应按 hit/miss/output 分别计价。按查询时 Flash 非高峰价（每百万 tokens 0.003/0.15/0.6 美元）估算上述同负载费用；该样本费用估算减少 59.51%。这仅为 usage 加权估算，不是账户账单，实际费率与时段以 [官方价格](https://api-docs.deepseek.com/quick_start/pricing/) 为准。

## 任务正确性和额外失败样本

所有纳入性能对照的运行均验证：精确目标文本、非目标正文/结构/格式保留、实际文件落盘与读回、最新 revision、每轮 fresh snapshot、最后重启仍读到正确内容。

性能基准的客户端是 headless EditorSession bridge：调用真实 Sidecar prepare，再校验版本并写入独立合成 JSON 文件。它证明确定性事务与模型工具链，不能替代浏览器 ProseMirror、用户审批或实际简历保存的验证。

额外基线第 7 次在第二轮失败：模型多次提交错误的 catalog_revision，Sidecar 正确拒绝，目标文字没有修改，精确文档断言拦住了模型口头报告的完成。该样本没有隐藏或当作成功；usage 和错误保留在本机 `artifacts/cache-efficiency/baseline-off-7.json`，摘要也收入结果 JSON。它没有完成八轮，单独报告，不混入完整八轮性能分母。不能根据这个个例断言某一种缓存机制必然导致模型填错参数。

## 思考历史与强制压缩

- High 模式额外八轮通过，实际产生 526 个 reasoning tokens；后续请求回放非空思考历史，重启后的两次调用分别回放 9 / 10 条含思考的 assistant 历史。累计命中 94.67%。
- 将产品预算显式压到 24k、ratio 0.55 的独立八轮场景确实触发 1 次压缩，随后精确修改、核对和重启断言全部通过。摘要请求命中 96.90%，压缩后首请求命中 69.00%。这些请求计入该场景合计，没有隐藏压缩成本。
- 强制场景只验证所覆盖的流程，不代表所有历史规模/图片输入都已逐一穷举。真实页面图片工具未在此性能基准调用。

## 真实浏览器验收

使用独立端口、数据目录、真实 Sidecar/Host 和 Chrome，导入合成简历，保持实际「手动应用」模式和 High 模型：

1. 请求岗位局部替换。出现“应用修改”之前，画布仍为原文；点击应用后，只改变指定岗位，其他可见正文精确相同。
2. 刷新页面后，新的岗位仍存在；Sidecar workspace-view 也返回已保存画布。
3. 请求工作方式替换，点击“保留原文”。内容与请求前完全相同，模型明确报告拒绝，没有自动重试写入。
4. 用户重新授权同一修改后，点击应用；模型准确报告人工确认与保存。只改变工作方式，刷新后保留。

第一轮浏览器发现模型将人工确认误述为自动执行；已在紧凑回执添加 mutation_mode/decision_source，并在结束证据说明 review 的结果来自用户决定。补测第 3–4 步确认修复，Host 回归同时覆盖 review/solo 的来源和未保存结果。

截图与合成持久化证据位于本机 `output/playwright/cache-efficiency/`。重启 Host 时出现一次预期的过期 session token 401，前端重新获取 token 后请求成功，没有持续鉴权失败。未修改 React 或 UI 控件。
